<p>Kubernetes can seem intimidating because it comes with a large vocabulary: Pods, Nodes, Services, Deployments, schedulers, controllers, and clusters.</p><p>But the basic idea is much simpler:</p><blockquote><strong><em>Kubernetes decides where applications should run, starts them, monitors them, and tries to keep them running.</em></strong></blockquote><h3>Start with a cluster</h3><p>A Kubernetes <strong>cluster</strong> is a group of computers working together.</p><p>These computers are called <strong>Nodes</strong>.</p><p>Instead of manually deciding which application should run on which machine, you describe what you want, and Kubernetes handles the placement.</p><p>For example, you might tell Kubernetes:</p><blockquote><em>Run three copies of my web application and restart any copy that fails.</em></blockquote><p>Kubernetes continuously works to maintain that desired state.</p><h3>Applications run inside Pods</h3><p>A <strong>Pod</strong> is the smallest unit Kubernetes schedules.</p><p>A Pod usually contains one main application container, although it can contain multiple closely related containers.</p><p>You can think of it like this:</p><pre>Cluster<br>  ├── Node 1<br>  │     ├── Pod A<br>  │     └── Pod B<br>  │<br>  └── Node 2<br>        └── Pod C</pre><p>Containers hold the application and its dependencies. Pods give Kubernetes a standard unit for running and managing those containers.</p><h3>The scheduler chooses a Node</h3><p>When a new Pod is created, the Kubernetes <strong>scheduler</strong> decides which Node should run it.</p><p>The scheduler considers factors such as:</p><ul><li>Available CPU and memory</li><li>Hardware requirements</li><li>Node labels</li><li>Placement policies</li><li>Resource availability</li><li>Workload constraints</li></ul><p>For example, a Pod might request:</p><pre>resources:<br>  requests:<br>    cpu: &quot;2&quot;<br>    memory: &quot;4Gi&quot;</pre><p>The scheduler searches for a Node that can satisfy those requirements.</p><p>For GPU workloads, the request might include an accelerator:</p><pre>resources:<br>  limits:<br>    nvidia.com/gpu: 1</pre><p>This tells Kubernetes that the workload needs access to one GPU exposed by the NVIDIA device plugin.</p><h3>The kubelet runs the workload</h3><p>Each Node runs an agent called the <strong>kubelet</strong>.</p><p>Once the scheduler selects a Node, the kubelet on that Node:</p><ol><li>Downloads the required container image</li><li>Starts the containers</li><li>Monitors the Pod</li><li>Reports its status to Kubernetes</li></ol><p>A useful mental model is:</p><pre>Scheduler: Where should the Pod run?</pre><pre>Kubelet: I will run it on this Node.</pre><h3>Controllers maintain the desired state</h3><p>Kubernetes does not only start applications. It continuously checks whether reality matches what you requested.</p><p>Suppose you create a Deployment that requests three application replicas:</p><pre>Desired state: 3 running Pods<br>Actual state: 2 running Pods</pre><p>A Kubernetes controller notices the difference and creates another Pod.</p><p>If one Node fails, Kubernetes can recreate the lost workload elsewhere, provided suitable capacity is available.</p><p>This process is often called <strong>self-healing</strong>, although it is better understood as continuous reconciliation.</p><p>Kubernetes repeatedly asks:</p><blockquote><em>Does the actual cluster state match the desired state?</em></blockquote><p>If not, it attempts to correct it.</p><h3>Deployments manage application replicas</h3><p>A <strong>Deployment</strong> is commonly used to manage stateless applications.</p><p>It specifies:</p><ul><li>The container image</li><li>The number of replicas</li><li>Resource requirements</li><li>Update behavior</li><li>Pod configuration</li></ul><p>A simplified example looks like this:</p><pre>apiVersion: apps/v1<br>kind: Deployment<br>metadata:<br>  name: example-app<br>spec:<br>  replicas: 3<br>  selector:<br>    matchLabels:<br>      app: example<br>  template:<br>    metadata:<br>      labels:<br>        app: example<br>    spec:<br>      containers:<br>        - name: application<br>          image: example/app:1.0</pre><p>This configuration tells Kubernetes to maintain three Pods running the specified image.</p><h3>Services provide stable access</h3><p>Pods are temporary. They may be restarted, recreated, or moved to different Nodes.</p><p>Their IP addresses can change.</p><p>A Kubernetes <strong>Service</strong> provides a stable network endpoint for a group of Pods.</p><p>Instead of sending traffic to a specific Pod, clients send traffic to the Service:</p><pre>User request<br>     ↓<br>Kubernetes Service<br>     ↓<br>One of several application Pods</pre><p>The Service finds the appropriate Pods through labels and distributes traffic among them.</p><h3>ConfigMaps and Secrets separate configuration</h3><p>Application configuration should not always be embedded inside a container image.</p><p>Kubernetes provides:</p><ul><li><strong>ConfigMaps</strong> for ordinary configuration</li><li><strong>Secrets</strong> for sensitive configuration such as tokens and credentials</li></ul><p>This allows the same container image to run with different settings across development, testing, and production environments.</p><h3>Kubernetes is declarative</h3><p>One of the most important Kubernetes ideas is that you usually describe the result you want rather than the exact sequence of commands required to produce it.</p><p>You say:</p><blockquote><em>I want three replicas of this application.</em></blockquote><p>You do not normally say:</p><blockquote><em>Start one container on Node A, another on Node B, and restart the second container if it fails.</em></blockquote><p>Kubernetes determines the actions needed to reach and maintain the desired state.</p><p>That is what makes Kubernetes <strong>declarative</strong>.</p><h3>Kubernetes in one workflow</h3><p>The full process can be summarized as:</p><pre>You submit a workload definition<br>             ↓<br>The API server stores the desired state<br>             ↓<br>The scheduler selects a suitable Node<br>             ↓<br>The kubelet starts the Pod<br>             ↓<br>Controllers monitor the cluster<br>             ↓<br>Kubernetes corrects failures or differences</pre><h3>What Kubernetes does not automatically solve</h3><p>Kubernetes is powerful, but it is not an automatic solution to every infrastructure problem.</p><p>It does not inherently guarantee:</p><ul><li>Efficient application code</li><li>High GPU utilization</li><li>Correct autoscaling policies</li><li>Optimal workload placement</li><li>Low infrastructure cost</li><li>Perfect security</li><li>Reliable data pipelines</li><li>Intelligent resource sharing</li></ul><p>Kubernetes provides the orchestration framework. Engineers must still define suitable resource requests, policies, monitoring, scheduling strategies, and operational safeguards.</p><h3>The one-sentence summary</h3><blockquote><strong><em>Kubernetes is a system that schedules containerized applications across multiple machines and continuously works to keep the actual system aligned with the desired configuration.</em></strong></blockquote><p>Once that mental model is clear, concepts such as Deployments, Services, autoscaling, GPU scheduling, and Dynamic Resource Allocation become much easier to understand.</p><h3>Disclaimer</h3><p>This article is intended for educational and informational purposes only.

<h3>Create tools, resources, and prompts, test them with MCP Inspector, and understand what happens behind the scenes</h3><p>You have learned what the Model Context Protocol is.</p><p>You understand that an MCP application generally involves:</p><ul><li>A host</li><li>An MCP client</li><li>An MCP server</li><li>Tools</li><li>Resources</li><li>Prompts</li></ul><p>The natural next question is:</p><blockquote><strong><em>How do I build one?</em></strong></blockquote><p>In this tutorial, we will create a small but complete MCP server in Python.</p><p>Our server will represent a fictional software-testing workspace. It will allow an MCP-compatible application to:</p><ul><li>Calculate a test-run completion rate</li><li>Compare two simple test summaries</li><li>Retrieve a testing guide as a resource</li><li>Generate a reusable investigation prompt</li><li>Inspect every capability through MCP Inspector</li></ul><p>By the end, you will understand not only how to write the code, but also what the SDK is doing for you, how an MCP client discovers your server’s capabilities, and how to diagnose common problems.</p><p>This tutorial uses the official Python SDK and its stable v1 FastMCP interface. The official SDK supports building MCP clients and servers and exposing tools, resources, and prompts through standard MCP transports.</p><h3>What we are going to build</h3><p>Our server will expose the following capabilities.</p><h3>Tools</h3><pre>calculate_completion(completed, total)<br>compare_test_runs(current_passed, current_total, baseline_passed, tutorial.</p><h3>Before you begin</h3><h3>Prerequisites</h3><p>You will need:</p><ul><li>Python 3.10 or newer</li><li>A terminal or command prompt</li><li>A code editor</li><li>uv This means you do not have to manually write JSON Schema, parse every MCP request, or implement the complete JSON-RPC protocol yourself.</p><p>For example:</p><pre>def calculate_completion(completed: int, total: int)</pre><p>tells the SDK that the tool accepts two integer arguments.</p><p>The docstring explains their meaning.</p><p>Together, the types and documentation become part of the tool description an MCP client can inspect.</p><h3>Step 4: Understand the first tool</h3><p>Our first tool is:</p><pre>@mcp.tool()<br>def calculate_completion(completed: int, total: int) -&gt; dict[str, Any]:</pre><p>The decorator:</p><pre>@mcp.tool()</pre><p>registers the function as an MCP tool.</p><p>MCP tools are server-exposed functions that models can discover and invoke. The MCP specification defines tools as named capabilities with metadata and an input schema. They may retrieve information, call APIs, or perform computations.</p><h3>Why the validation matters</h3><p>The function checks:</p><pre>if total &lt;= 0:<br>    raise ValueError(&quot;total must be greater than zero&quot;)</pre><p>It also prevents:</p><ul><li>Negative counts</li><li>Completed counts greater than total counts</li><li>Division by zero</li></ul><p>A language model might submit incorrect arguments.</p><p>An MCP schema can verify basic types, but your server must still validate whether the values make sense.</p><p>This is an important production rule:</p><blockquote><strong><em>Never assume that schema-valid tool arguments are semantically valid or authorized.</em></strong></blockquote><p>The tool then performs a deterministic calculation:</p><pre>completion_percentage = round((completed / total) * 100, 2)</pre><p>The model is not trusted to calculate the authoritative metric.</p><p>The Python code calculates it.</p><p>The tool returns structured data:</p><pre>return {<br>    &quot;completed&quot;: completed,<br>    &quot;total&quot;: total,<br>    &quot;incomplete&quot;: total - completed,<br>    &quot;completion_percentage&quot;: completion_percentage,<br>}</pre><p>Structured results are easier for clients and models to interpret than a loosely formatted sentence.</p><h3>Step 5: Understand the run-comparison tool</h3><p>Our second tool compares two pass rates:</p><pre>@mcp.tool()<br>def compare_test_runs(...):</pre><p>It returns:</p><ul><li>Current pass rate</li><li>Baseline pass rate</li><li>Difference in percentage points</li><li>Direction of movement</li></ul><p>Suppose the current run has:</p><pre>86 passes out of 100</pre><p>and the baseline has:</p><pre>94 passes out of 100</pre><p>The tool returns a difference of:</p><pre>-8.0 percentage points</pre><p>Notice that we use <strong>percentage points</strong>, not “percent decrease.”</p><p>A movement from 94% to 86% is an 8-percentage-point decrease. The relative percentage decrease is a different calculation.</p><p>Being precise about metric definitions is especially important when AI-generated explanations are placed on top of deterministic results.</p><h3>Why not let the AI calculate this?</h3><p>An AI model could calculate it correctly.</p><p>It could also:</p><ul><li>Confuse percentage points with relative percentage</li><li>Use the wrong denominator</li><li>Mix scheduled and completed tests</li><li>Round inconsistently</li><li>Compare unrelated runs</li></ul><p>A small deterministic tool makes the calculation reproducible and testable.</p><h3>Step 6: Understand the resource</h3><p>The server exposes this resource:</p><pre>@mcp.resource(&quot;testing-guide://regression/basics&quot;)<br>def get_regression_testing_guide() -&gt; str:</pre><p>A resource exposes contextual information through a URI-like identifier.</p><p>Our identifier is:</p><pre>testing-guide://regression/basics</pre><p>The resource returns a short document explaining regression-testing concepts.</p><p>Unlike a tool, the resource does not perform a calculation. It provides context that an MCP application may retrieve and place into a model’s context.</p><p>Resources can represent:</p><ul><li>Documents</li><li>Configuration records</li><li>Database-derived data</li><li>Schemas</li><li>Reports</li><li>Application state</li><li>Generated content</li></ul><p>The stable MCP specification distinguishes resources from tools and prompts: resources provide context and data, prompts provide templated messages or workflows, and tools provide functions the model may invoke.</p><h3>Static and templated resources</h3><p>Our resource has one fixed URI:</p><pre>testing-guide://regression/basics</pre><p>A templated resource might look like:</p><pre>@mcp.resource(&quot;test-run://{run_id}/summary&quot;)<br>def get_test_run_summary(run_id: str) -&gt; str:<br>    ...</pre><p>That would allow the client to request different resources using different run identifiers.</p><p>We will keep this first project simple and use a static resource.</p><h3>Step 7: Understand the prompt</h3><p>Our prompt is:</p><pre>@mcp.prompt()<br>def investigate_test_run(<br>    current_run: str,<br>    baseline_run: str,<br>    audience: str = &quot;validation engineer&quot;,<br>) -&gt; str:</pre><p>The prompt generates a reusable investigation template.</p><p>For example, a client could request it using:</p><pre>current_run = RUN-2048<br>baseline_run = RUN-2015<br>audience = engineering manager</pre><p>The result would instruct the model to compare the two runs and structure the response for an engineering manager.</p><h3>Why use an MCP prompt?</h3><p>A prompt is useful when you want a reusable, discoverable workflow such as:</p><ul><li>Investigate a failed build</li><li>Summarize a release</li><li>Compare two regression runs</li><li>Review a configuration</li><li>Prepare a daily report</li></ul><p>The prompt keeps the expected structure consistent.</p><p>However, it is not a policy engine.</p><p>A prompt can tell the model not to overstate root cause, but access control and operational restrictions must still be implemented outside the prompt.</p><h3>Step 8: Start the server</h3><p>The final lines are:</p><pre>if __name__ == &quot;__main__&quot;:<br>    logger.info(&quot;Starting MCP Test Assistant&quot;)<br>    mcp.run(transport=&quot;stdio&quot;)</pre><p>This starts the server using the <strong>stdio transport</strong>.</p><p>With stdio:</p><ol><li>An MCP client launches the server as a subprocess.</li><li>The client sends MCP protocol messages through standard input.</li><li>The server returns protocol messages through standard output.</li><li>Diagnostic logs should be written to standard error.</li></ol><p>The official documentation warns that ordinary output written to stdout can corrupt a stdio MCP connection because stdout carries the JSON-RPC message stream. happens during MCP discovery?</h3><p>When Inspector connects, it does not simply begin calling random Python functions.</p><p>The client and server first initialize their connection and negotiate supported protocol capabilities.</p><p>During operation, the client can request lists of:</p><ul><li>Tools</li><li>Resources</li><li>Prompts</li></ul><p>The server returns metadata describing what it provides.</p><p>For a tool, this includes:</p><ul><li>Name</li><li>Description</li><li>Input schema</li></ul><p>For a resource, this may include:</p><ul><li>URI</li><li>Name</li><li>Description</li><li>MIME type</li></ul><p>For a prompt, this includes:</p><ul><li>Name</li><li>Description</li><li>Arguments</li></ul><p>The client should only use successfully negotiated capabilities and the agreed protocol version.</p><p>When the client invokes a tool, the high-level exchange is conceptually similar to:</p><pre>{<br>  &quot;method&quot;: &quot;tools/call&quot;,<br>  &quot;params&quot;: {<br>    &quot;name&quot;: &quot;calculate_completion&quot;,<br>    &quot;arguments&quot;: {<br>      &quot;completed&quot;: 87,<br>      &quot;total&quot;: 100<br>    }<br>  }<br>}</pre><p>You do not have to manually implement this JSON-RPC handling because the SDK manages it.</p><h3>Step 13: Organize the project as causes:</p><ul><li>The command is wrong</li><li>The virtual environment is not active</li><li>uv is not installed</li><li>The server path is incorrect</li><li>The MCP package was installed in another environment</li></ul><p>Try running the server command directly:</p><pre>uv run server.py</pre><p>For a stdio server, it may appear to wait silently. That is expected: it is waiting for protocol input from a client.</p><p>Check the interpreter and package:</p><pre>which python<br>python -m pip show mcp</pre><p>On Windows:</p><pre>Get-Command python<br>python -m pip show mcp</pre><h3>Problem 2: ModuleNotFoundError: No module named &#39;mcp&#39;</h3><p>The package is not installed in the Python environment being used to launch the server.</p><p>With uv:</p><pre>uv sync<br>uv run server.py</pre><p>With pip:</p><pre>python -m pip install &quot;mcp[cli]&gt;=1.2,&lt;2&quot;<br>python server.py</pre><p>Verify that python and pip refer to the same environment:</p><pre>python -m pip --version<br>python --version</pre><h3>Problem 3: The server disconnects after adding print()</h3><p>For a stdio server, stdout carries MCP messages.</p><p>This is unsafe:</p><pre>print(&quot;Starting server&quot;)</pre><p>Use logging:</p><pre>logger.info(&quot;Starting server&quot;)</pre><p>Or explicitly write to stderr:</p><pre>import sys</pre><pre>print(&quot;Starting server&quot;, file=sys.stderr)</pre><p>The official MCP documentation specifically warns that stdout logging can corrupt stdio protocol communication.</p><h3>Problem 4: A tool does not appear in Inspector</h3><p>Check:</p><ul><li>Is the function decorated with @mcp.tool()?</li><li>Is the decorator executed before mcp.run()?</li><li>Did you save the file?</li><li>Did you reconnect Inspector?</li><li>Did the module fail during import?</li><li>Does the startup log show an exception?</li></ul><p>After changing the server:</p><ol><li>Stop the old process</li><li>Restart or reconnect Inspector</li><li>Verify the tool list again</li></ol><p>The official Inspector workflow recommends reconnecting after server changes and retesting the affected capabilities.</p><h3>Problem 5: The tool receives incorrect argument types</h3><p>Use clear type annotations:</p><pre>def calculate_completion(completed: int, total: int)</pre><p>Avoid ambiguous definitions such as:</p><pre>def calculate_completion(data)</pre><p>Type annotations improve the generated schema, but the function should still validate its input.</p><h3>Problem 6: The model selects the wrong tool</h3><p>This is often a tool-design problem rather than a protocol failure.</p><p>Avoid vague tools such as:</p><pre>process_data<br>do_task<br>run_operation</pre><p>Prefer names and descriptions that communicate intent:</p><pre>calculate_test_completion<br>compare_test_runs<br>get_regression_summary</pre><p>A tool should explain:</p><ul><li>What it does</li><li>What it does not do</li><li>What each argument means</li><li>Whether it changes state</li><li>What it returns</li></ul><p>Do not hide critical safety instructions only inside a tool description. The server must enforce them.</p><h3>Problem 7: Relative file paths work in the terminal but fail in a host</h3><p>An MCP host may launch your server from a different working directory.</p><p>This can break:</p><pre>open(&quot;data/config.json&quot;)</pre><p>Resolve paths relative to the module:</p><pre>from pathlib import Path</pre><pre>BASE_DIR = Path(__file__).resolve().parent<br>CONFIG_PATH = BASE_DIR / &quot;data&quot; / &quot;config.json&quot;</pre><p>The official debugging guidance recommends using absolute paths because the working directory of a client-launched stdio server may be undefined or different from your terminal.</p><h3>Problem 8: Environment variables are missing</h3><p>A terminal session and an MCP host may not have the same environment.</p><p>Do not assume that a host can see:</p><pre>API_TOKEN<br>DATABASE_URL<br>PROJECT_PATH</pre><p>Use explicit environment configuration and validate required settings at startup.</p><p>Never include secrets in:</p><ul><li>Tool descriptions</li><li>Prompt text</li><li>Resource output</li><li>Logs</li><li>Error messages</li></ul><h3>Common mistakes when building a first MCP server</h3><h3>Mistake 1: Starting with a tool that can do anything</h3><p>A beginner may create:</p><pre>execute_shell_command(command)</pre><p>This is powerful but difficult to secure.</p><p>Start with narrow, read-only tools.</p><p>Better:</p><pre>get_test_run_summary(run_id)</pre><h3>Mistake 2: Mixing tool execution with AI reasoning</h3><p>A tool should return authoritative data.</p><p>It should not pretend that a language-model hypothesis is a verified system result.</p><p>For example:</p><pre>Tool:<br>Return the current and baseline run metrics.</pre><pre>AI:<br>Explain possible reasons for the difference.</pre><pre>Engineer:<br>Review whether the explanation is credible.</pre><h3>Mistake 3: Using prompts as security controls</h3><p>This is not sufficient:</p><pre>“Never call the destructive tool without approval.”</pre><p>The host or server must enforce approval and authorization in code.</p><h3>Mistake 4: Returning huge amounts of raw data</h3><p>Avoid returning an entire multi-gigabyte log through one tool.</p><p>Instead expose narrow operations:</p><pre>get_error_summary<br>get_log_window<br>search_failure_signature<br>get_crash_metadata</pre><p>Large outputs increase latency, context consumption, privacy risk, and the chance that relevant evidence will be overlooked.</p><h3>Mistake 5: Returning secrets in exceptions</h3><p>Avoid:</p><pre>raise RuntimeError(<br>    f&quot;Authentication failed using token {api_token}&quot;<br>)</pre><p>Use:</p><pre>raise RuntimeError(&quot;Authentication failed&quot;)</pre><p>Store detailed sensitive diagnostics only in an appropriately protected server log.</p><h3>Mistake 6: Confusing local development with production readiness</h3><p>A local stdio server is excellent for learning.</p><p>A production remote server may require:</p><ul><li>Authentication</li><li>Authorization</li><li>TLS</li><li>Secret management</li><li>Rate limiting</li><li>Timeouts</li><li>Audit logs</li><li>Observability</li><li>Data classification</li><li>Tenant isolation</li><li>Approval workflows</li><li>Deployment hardening</li><li>Incident response</li></ul><p>A working demo is not automatically a secure enterprise service.</p><h3>How to improve this project next</h3><p>Once the local server works, you can extend it gradually.</p><h3>Improvement 1: Add a templated resource</h3><pre>@mcp.resource(&quot;test-run://{run_id}/summary&quot;)<br>def get_run_summary(run_id: str) -&gt; str:<br>    return f&quot;Summary for test run {run_id}&quot;</pre><p>Replace the placeholder with an approved database or API call later.</p><h3>Improvement 2: Add structured domain models</h3><p>Define explicit data models for:</p><ul><li>Test runs</li><li>Results</li><li>Failures</li><li>Configurations</li><li>Artifacts</li></ul><h3>Improvement 3: Add timeout handling</h3><p>External requests should not wait forever.</p><p>Use explicit timeouts for:</p><ul><li>HTTP APIs</li><li>Databases</li><li>File operations</li><li>Subprocesses</li></ul><h3>Improvement 4: Add authorization</h3><p>Before returning data, verify:</p><ul><li>Who is requesting it</li><li>Which project they can access</li><li>Whether the resource is restricted</li><li>Whether the operation is read-only or write-enabled</li></ul><h3>Improvement 5: Add a remote transport</h3><p>After the local server is reliable, explore Streamable HTTP.</p><p>The official Python SDK supports stdio and Streamable HTTP, while the MCP architecture generally associates stdio with local subprocess servers and Streamable HTTP with independently hosted remote servers.</p><h3>Improvement 6: Add approved operational tools</h3><p>Examples:</p><pre>create_issue_draft<br>request_test_rerun<br>generate_candidate_test_list</pre><p>Do not begin with destructive operations.</p><h3>A safer progression from demo to production</h3><p>A sensible sequence is:</p><pre>1. Static resource<br>        ↓<br>2. Read-only deterministic tool<br>        ↓<br>3. Approved external API lookup<br>        ↓<br>4. Authentication and authorization<br>        ↓<br>5. Structured logs and monitoring<br>        ↓<br>6. Human-approved reversible action<br>        ↓<br>7. Policy-constrained operational workflow</pre><p>This sequence makes failures easier to understand and limits the impact of early mistakes.</p><h3>Final code</h3><p>For convenience, here is the complete beginner version again:</p><pre>from __future__ import annotations</pre><pre>import logging<br>from typing import Any</pre><pre>from mcp.server.fastmcp import FastMCP<br></pre><pre>logging.basicConfig(<br>    level=logging.INFO,<br>    format=&quot;%(asctime)s %(levelname)s %(name)s: %(message)s&quot;,<br>)</pre><pre>logger = logging.getLogger(&quot;mcp-test-assistant&quot;)</pre><pre>mcp = FastMCP(&quot;MCP Test Assistant&quot;)<br></pre><pre>@mcp.tool()<br>def calculate_completion(completed: int, total: int) -&gt;

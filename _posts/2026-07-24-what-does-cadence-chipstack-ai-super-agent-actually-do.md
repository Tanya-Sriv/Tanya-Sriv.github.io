Please refer to official Cadence resources for current and authoritative product information.</em></blockquote><p>AI is beginning to move beyond code suggestions and chat interfaces.</p><p>In semiconductor engineering, newer AI systems are being designed to read hardware requirements, modify RTL, generate tests, run verification tools, investigate failures, and decide what to try next.</p><p>Cadence ChipStack AI Super Agent is one example.</p><p>But what does it actually do, and how is it different from an ordinary AI coding assistant?</p><p>Let us break it down without the marketing language.</p><h3>First, what is RTL?</h3><p><strong>RTL stands for Register-Transfer Level.</strong></p><p>It is code, usually written in SystemVerilog, Verilog, or VHDL, that describes digital hardware.</p><p>RTL may represent:</p><ul><li>A command queue</li><li>A GPU scheduler</li><li>A cache controller</li><li>A memory interface</li><li>A state machine</li><li>A power-management block</li></ul><p>RTL looks like software, but it does not become instructions executed by a CPU.</p><p>It becomes physical logic.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*22mnUuMiCPCQiQHGAQPzcw.gif" /></figure><pre>Software code -&gt; Compiler -&gt; Instructions executed by a processor -&gt; RTL code -&gt; Synthesis and physical-design tools -&gt; Logic gates, registers, and physical wires</pre><p>The easiest mental model is:</p><blockquote><em>Software tells an existing processor what to do. RTL describes the processor or hardware that should exist.</em></blockquote><h3>Writing RTL is only half the work</h3><p>After engineers create RTL, they must verify that it behaves correctly.</p><p>Verification asks questions such as:</p><ul><li>Does the hardware follow the specification?</li><li>Does it handle reset correctly?</li><li>Can it deadlock?</li><li>Can a queue overflow?</li><li>What happens when several requests arrive together?</li><li>Does the logic behave correctly under backpressure?</li><li>Have important corner cases been tested?</li></ul><p>For GPUs, this becomes especially difficult because many operations happen at the same time.</p><p>A bug may appear only when:</p><ul><li>Several commands overlap</li><li>A cache miss occurs during a power-state change</li><li>Multiple clients compete for one resource</li><li>Reset arrives while a transaction is incomplete</li></ul><p>That means verification often requires far more than running a few normal tests.</p><h3>The familiar regression workflow</h3><p>Most validation and CI/CD engineers already know this loop:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*B9fz_EihF-mfOQgpisTqNQ.gif" /></figure><p>CI/CD systems automate much of the execution.</p><p>They can schedule jobs, collect logs, retry failures, and update dashboards.</p><p>But they usually do not understand:</p><ul><li>Which requirement was violated</li><li>Whether the RTL or testbench is wrong</li><li>Which assertion is missing</li><li>Which test should run next</li><li>Whether several failures share one root cause</li></ul><p>ChipStack is intended to work at this engineering-decision layer.</p><h3>ChipStack in one sentence</h3><p><strong>ChipStack is an AI-driven system that coordinates specialized agents to perform parts of RTL design, verification, regression analysis, and debugging.</strong></p><p>It is not simply one chatbot generating SystemVerilog.</p><p>Think of it more like an AI-assisted hardware engineering team.</p><h3>A virtual design and verification team</h3><p>Imagine giving the system this goal:</p><blockquote><em>Add starvation protection to a GPU command scheduler and verify that normal-priority work is eventually executed.</em></blockquote><p>Different agents may handle different tasks.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*RAV3zJzMLglpvAyG7EHUkg.gif" /><figcaption>The ChipStack team</figcaption></figure><p>The important point is that these agents are intended to work from shared design context rather than independently interpreting unrelated files.</p><h3>What is the shared mental model?</h3><p>Cadence describes ChipStack as maintaining a structured representation of the design.</p><p>This may include:</p><ul><li>Specifications</li><li>Existing RTL</li><li>Module hierarchy</li><li>Interfaces</li><li>Testbenches</li><li>Assertions</li><li>Previous design history</li><li>Verification results</li></ul><p>A software analogy would be an AI coding assistant that understands not only one file, but also:</p><ul><li>The repository architecture</li><li>API contracts</li><li>Service dependencies</li><li>Test ownership</li><li>Historical failures</li><li>Design decisions</li></ul><h3>Visual: Shared context</h3><pre>Specifications ─────┐<br>Existing RTL ───────┤<br>Testbenches ────────┤<br>Design hierarchy ───┼──&gt; Shared design model<br>Historical results ─┤<br>Interfaces ─────────┘<br>                           ↓<br>              RTL, test, formal, and debug agents</pre><p>This does not mean the system understands the design exactly like a senior engineer.</p><p>It means the agents operate from a common structured view of the project.</p><h3>A realistic GPU example</h3><p>Suppose a GPU scheduler has two queues:</p><pre>High-priority work<br>Normal-priority work</pre><p>The new requirement is:</p><blockquote><em>High-priority work should normally run first, but normal work must not wait forever.</em></blockquote><p>That sounds simple, but the implementation must answer several questions:</p><ul><li>How long may normal work wait?</li><li>Does waiting time continue during backpressure?</li><li>What happens during reset?</li><li>What if both queues remain full?</li><li>What if priority changes while a command waits?</li><li>Can two commands be selected together?</li></ul><p>Here is how ChipStack might assist.</p><h3>From requirement to verified RTL</h3><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*t0Yg9kmHASEpxFSKMA1xDQ.gif" /><figcaption>From requirement to verified RTL</figcaption></figure><p><strong>1: Engineer provides the goal</strong></p><pre>Add priority scheduling with starvation protection</pre><p><strong>2: ChipStack examines the design</strong></p><pre>Relevant module found: gpu_scheduler.sv<br>Related tests and assertions identified</pre><p><strong>3: RTL agent proposes a change</strong></p><pre>Add an age counter for waiting commands<br>Modify arbitration logic<br>Add configurable starvation threshold</pre><p><strong>4: Verification agents create checks</strong></p><pre>Test high-priority traffic<br>Test normal traffic<br>Test continuous mixed traffic<br>Test reset<br>Test backpressure<br>Test threshold limits</pre><p><strong>5: Formal verification finds a problem</strong></p><pre>Normal work can still starve when backpressure<br>and repeated high-priority arrivals occur together</pre><p><strong>6: Debug agent identifies the cause</strong></p><pre>Age counter resets after a blocked grant</pre><p><strong>7: RTL agent revises the design</strong></p><pre>Preserve command age while downstream logic is blocked</pre><p><strong>8: Tools run again</strong></p><pre>Simulation passes<br>Formal property passes<br>Coverage improves</pre><p><strong>9: Engineer reviews the result</strong></p><pre>View RTL diff<br>Review assertion<br>Inspect failing trace<br>Approve, edit, or reject</pre><p>This loop is the main difference between simple code generation and agentic engineering.</p><h3>Why not use an ordinary LLM?</h3><p>A normal LLM can produce RTL that looks reasonable.</p><p>But reasonable-looking hardware can still be wrong.</p><p>For example, generated RTL may:</p><ul><li>Compile but violate the architecture</li><li>Work during normal traffic but deadlock under pressure</li><li>Mishandle reset</li><li>Lose data in one unusual sequence</li><li>Pass incomplete generated tests</li><li>Introduce timing or power problems</li></ul><p>A language model saying that the code is correct is not engineering evidence.</p><p>ChipStack’s intended workflow adds verification tools to the loop.</p><h3>LLM versus engineering agent</h3><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*WZ0zqtvlwqR5tGo9xfmT5Q.gif" /></figure><p><strong>Ordinary generation</strong></p><pre>Prompt<br>  ↓<br>Generated RTL<br>  ↓<br>Looks correct</pre><p><strong>Tool-grounded workflow</strong></p><pre>Requirement<br>  ↓<br>Generated RTL and tests<br>  ↓<br>Simulation and formal verification<br>  ↓<br>Failure evidence<br>  ↓<br>Revision<br>  ↓<br>Engineer review</pre><p>The second process is still not guaranteed to produce a correct design.</p><p>It simply provides stronger evidence than text generation alone.</p><h3>What does formal verification add?</h3><p>Simulation checks the test cases that engineers run.</p><p>Formal verification attempts to prove that a property cannot fail under any legal behavior represented by the model.</p><p>For example:</p><pre>The queue count must never exceed its capacity.</pre><p>Or:</p><pre>A valid command must not disappear without being completed or rejected.</pre><h3>Quick comparison</h3><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*WaCbLp6XUfMYZoHOieBBIw.png" /><figcaption>Simulation vs Formal verification</figcaption></figure><p>Formal verification is especially useful when evaluating AI-generated RTL.</p><p>However, it still depends on correct assumptions and properties.</p><p>Proving the wrong requirement does not make the design correct.</p><h3>How is ChipStack different from regression infrastructure?</h3><p>The two solve different problems.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*AGx7YF_Hfb-obm2YkgmsFw.png" /><figcaption>ChipStack vs Regression</figcaption></figure><p>ChipStack would still depend on reliable infrastructure underneath it.</p><p>The system needs:</p><ul><li>Compute scheduling</li><li>License management</li><li>Artifact storage</li><li>Version control</li><li>Reproducible environments</li><li>Access control</li><li>Dashboards</li><li>Failure recovery</li></ul><p>AI agents do not replace the infrastructure. They create new workloads for it.</p><h3>What would engineers actually review?</h3><p>An engineer would need visibility into information such as:</p><pre>Goal<br>Tasks selected by the agents<br>Files examined<br>Proposed RTL changes<br>Generated tests<br>Assertions<br>Formal results<br>Simulation results<br>Failure traces<br>Root-cause explanation<br>Proposed correction<br>Execution history</pre><p>A simplified interaction could look like this:</p><pre>Goal: Add starvation protection</pre><pre>✓ Scheduler RTL updated<br>✓ Six tests generated<br>✓ Three assertions generated<br>✗ Fairness assertion failed</pre><pre>Cause:<br>Age counter resets when a blocked grant occurs.</pre><pre>Proposed fix:<br>Preserve age until the command is accepted.</pre><pre>Actions:<br>[View RTL diff] [View trace] [Run again] [Reject]</pre><p>The exact product interface may differ. This illustration shows the kind of evidence an engineer would need.</p><h3>Where ChipStack fits in GPU development</h3><p>ChipStack is most relevant to:</p><ul><li>GPU RTL development</li><li>Pre-silicon verification</li><li>UVM testbench development</li><li>Assertion generation</li><li>Formal verification</li><li>Regression triage</li><li>Failure debug</li><li>Design modifications</li></ul><p>It is not primarily intended for:</p><ul><li>GPU driver CI</li><li>Vulkan or OpenGL testing</li><li>Game benchmarking</li><li>Post-silicon device farms</li><li>Firmware release pipelines</li><li>Application profiling</li><li>Final physical chip layout</li><li>Laboratory validation of fabricated GPUs</li></ul><p>It operates mainly before the chip is manufactured.</p><h3>Where human expertise remains essential</h3><p>ChipStack can automate work, but it cannot remove engineering responsibility.</p><p>Humans must still decide:</p><ul><li>What the hardware should do</li><li>Whether the specification is precise</li><li>Whether the architecture is safe</li><li>Whether verification is sufficiently independent</li><li>Whether performance and power are acceptable</li><li>Whether generated changes follow internal methodology</li><li>Whether the evidence is strong enough for signoff</li></ul><p>One particularly important risk is circular verification.</p><pre>AI interprets requirement incorrectly<br>          ↓<br>AI generates RTL using that interpretation<br>          ↓<br>AI generates tests using the same interpretation<br>          ↓<br>Tests pass<br>          ↓<br>Actual requirement is still violated</pre><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*bN_dtFm3J358gUJBM6t2aQ.gif" /></figure><p>Independent review remains essential.</p><h3>What this means for GPU infrastructure engineers</h3><p>The most important change may be the arrival of <strong>agent-generated verification workloads</strong>.</p><p>Today, engineers usually initiate regressions and analysis jobs.</p><p>In an agentic environment, an AI system may repeatedly launch:</p><ul><li>Simulations</li><li>Formal jobs</li><li>Coverage analysis</li><li>Targeted reruns</li><li>Reproduction attempts</li><li>Design experiments</li></ul><p>Infrastructure may therefore need new controls.</p><h3>Possible requirements</h3><pre>Maximum compute per AI task<br>Maximum concurrent jobs<br>License-use limits<br>Retry limits<br>Storage limits<br>Approval gates<br>Agent and model version tracking<br>Prompt and specification traceability<br>Tool-version tracking<br>Human approval history</pre><p>Dashboards may also need to answer new questions:</p><ul><li>Why did the agent launch this job?</li><li>Which requirement is it investigating?</li><li>How much compute has it consumed?</li><li>Is it repeating the same unsuccessful loop?</li><li>Which proposed changes are waiting for review?</li><li>Can the complete run be reproduced?</li></ul><p>This is where AI-assisted hardware design directly intersects with CI/CD and validation infrastructure.</p><h3>The simplest final mental model</h3><p>Do not think of ChipStack as merely:</p><pre>ChatGPT for RTL</pre><p>Think of it as:</p><pre>Engineering goal<br>       ↓<br>Shared design understanding<br>       ↓<br>Specialized RTL, test, formal, and debug agents<br>       ↓<br>Simulation and verification tools<br>       ↓<br>Evidence and failures<br>       ↓<br>Revision<br>       ↓<br>Human engineer approval</pre><p>ChipStack is intended to automate parts of the path between a hardware requirement and verified RTL.</p><p>The AI may help decide what to generate, what to test, what failed, and what to try next.</p><p>The tools provide engineering evidence.</p><p>The infrastructure ensures the work runs securely and reproducibly.</p><p>The human engineer remains responsible for deciding whether the hardware is actually correct.</p><h3>Quick takeaway</h3><p><strong>ChipStack is not just an RTL generator.</strong></p><p>It is an agent-based workflow for coordinating:</p><pre>Specification<br>→ RTL<br>→ Tests<br>→ Formal verification<br>→ Simulation<br>→ Failure analysis<br>→ Revision<br>→ Engineer review</pre><p>For GPU engineers, it is most relevant to RTL and pre-silicon verification.</p><p>For GPU infrastructure engineers, it introduces a new challenge: supporting autonomous engineering workloads without losing control of compute, traceability, security, or review.</p>
